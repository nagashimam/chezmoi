# Agent Team Workflow

複数AIエージェント（Claude Code, Codex, Antigravity CLI）がHerdr上で協調し、5段階のフェーズ（Collect, Analyze, Define, Architect, Implement）を経てタスクを完了し、Draft PRを作成する完全自律型開発ワークフローです。
このスキルを実行するエージェントが「**オーケストレーター**」として全体の進行、Herdrペイン管理、合否判定、差し戻し制御を担当します。

## 適用範囲と完了条件

このワークフローは、要件整理、設計、実装、検証を含む開発タスクに適用します。調査のみ、文書のみ、または既存の小さな変更など、全5ステップを必要としないタスクでは、不要なステップを省略し、その理由を `task-background.md` に記録します。

タスク開始時に、依頼内容、対象リポジトリ、必須情報ソース、期待する成果物、実行可能な検証方法を確認します。不明点があっても安全に仮定できる場合は、その仮定を記録して進めます。要件や権限について人間の判断が必要な場合は、該当作業を保留します。

完了条件は、適用対象の全ステップがPASSし、実施できない検証と人間による確認項目が明記され、Draft PRを作成できたことです。Draft PRを作成できない場合は、理由と残作業を報告し、作業を完了扱いにしません。

### 軽量版（小さな変更向け）

次の条件をすべて満たすタスクでは、Step 2〜4 を1つの `plan.md` に統合する軽量版を使えます。数値は目安であり、迷う場合は通常版を使います。

- 変更ファイルが3つ以下で、追加・変更行が約150行以下に収まる見込みである。
- 新しい公開インターフェース、DBスキーマ、インフラ、権限、決済・認証の挙動を変更しない。
- 例: テストの `fixme` の整理や根拠の追記、ドキュメント・コメント・メッセージの修正、既存パターンに沿った小さなテストの追加。

軽量版の手順:

- Step 1 と Step 5（実装・QA・最終監査）は通常版と同じです。
- Step 2〜4 の代わりに、作業者 (Claude Code) が `plan.md` を1つ作成します。内容は「受入条件（Given-When-Then）」「テスト仕様（自動 / エージェント / 手動の分類つき）」「設計の要点（変更するファイルと理由、関係する ISO/IEC 25010 特性のみ）」「前提・制約・スコープ外」です。
- レビュワー (Codex) が `plan.md` を審査し、`review-plan.md` に出力します。合否判定プロトコルと差し戻し上限は通常版と同じです。
- Step 5 の入力は `plan.md` です。`PRD.md`、`system-design.md` などの個別ファイルは作りません。
- 軽量版を選んだ理由と、省略したステップを `task-background.md` に記録します。作業中に条件を超えた場合（行数の超過、新しい公開インターフェースの発生など）は、通常版に切り替えて Step 2〜4 を実施します。

## ツールと操作の範囲

- Herdr、Claude Code (`claude --permission-mode auto`)、Codex (`codex --approve-for-me`)、Antigravity CLI (`agy --sandbox` 起動後に Herdr で `shift+tab` を2回送信して auto モード化) は、利用可能で認証済みの場合に限り使用します。
- GitHub、Notion、Slack、Google Drive等の外部ソースは、依頼に含まれるもの、またはタスクに必要でアクセス権があるものだけ参照します。アクセスできない情報を推測で補いません。
- コマンドは、対象リポジトリ内で必要な読み取り、編集、ビルド、テストに限ります。テスト用ローカルサーバーはQAに必要な場合のみ起動し、終了後に停止します。
- 本番環境への変更、外部ユーザーへの連絡、データの削除、履歴を書き換えるGit操作（force push等）は実行しません。
- Git操作は、開始時の作業ツリーを確認してから行います。既存のユーザー変更を上書き、削除、コミット対象へ混入させません。
- ブランチ作成、コミット、リモートへのpush、Draft PR作成は本ワークフローで許可します。ただし、既存ブランチやPRとの衝突がある場合は別名を使用し、既存の作業を上書きしません。
- 必要なCLI、認証、権限が利用できない場合は、可能なローカル作業を進め、実行できなかった操作と理由を記録します。pushまたはDraft PR作成が必須のタスクでは、当該操作の前で停止して人間に依頼します。

## エージェントの強みと役割分担

| エージェント | 主要な強み | 担う役割 |
|---|---|---|
| **Claude Code** (`claude`) | **自律的なタスク実行・実装推進力** | 情報収集の実装、テスト仕様切り出し、システム設計、プロダクションコード実装 |
| **Codex** (`codex`) | **厳密なタスク実行・論理検証** | 仕様レビュー（PRD・テスト仕様・アーキテクチャ）、コード・エビデンス監査 |
| **Antigravity CLI** (`agy`) | **大規模NLP・文書読解 & Chromeブラウザ操作/QA** | 原文ハルシネーション検証、PRD統合、ブラウザ操作を含むQAテスト実走 |

### フェーズ別マトリクス

## 運用共通ルール

1. **進行・保留・停止の判断**:
   - **続行**: 任意ソースにアクセスできない場合、または一部のテストを実行できない場合は、その事実、影響、代替手段を成果物に記録し、残りの作業を続けます。
   - **フェーズ保留**: 必須ソースへのアクセス不可、重大な要件矛盾、既存の未コミット変更との安全な共存不可、必要な権限不足など、正確性または安全性に関わる判断が人間にしかできない場合は、影響する作業を保留します。独立して安全に進められる作業は続けます。
   - **納品保留**: QAまたは最終レビューがFAIL、結果を信頼できる形で取得できない、機密情報の混入を排除できない場合は、コミット・push・Draft PR作成を行いません。
   - **全体停止**: リポジトリ破損のおそれ、秘密情報の漏えい、取り消せない操作が必要など、安全に続行できない場合は全作業を停止し、状況と必要な判断を人間に報告します。
   - 保留または停止の報告には、理由、影響範囲、完了済み作業、再開に必要な判断・情報を含めます。
2. **FAIL時の差し戻し回数**:
   - 初回レビューまたはQAを判定0回目とし、FAIL後の修正・再判定を最大3回行います。つまり、判定は最大4回です。
   - 3回の修正後もPASSしない場合は、該当フェーズをBlockedとして保留し、人間に報告します。
   - 各ステップのレビューFAILとStep 5のQA／コードレビューFAILに同じ上限を適用します。修正後は、該当するレビューまたはQAを必ず再実行します。
   - **上限に数える指摘（重大度タグ）**: レビュワーとQAは、指摘ごとに `[blocking]` または `[non-blocking]` を付け、一行で理由を書きます。
     - `[blocking]`: 実装コード、テストコード、PRに含まれる内容の変更につながる指摘。要件・期待値の誤りや漏れ、テストの未カバー、設計と実装の不整合、バグ、セキュリティ、機密情報の混入などです。
     - `[non-blocking]`: 作業用文書の表現、件数や番号の整合、書式、追跡性の補足など、実装・テスト・PRの内容を変えない指摘です。
   - `STATUS: FAIL` にするのは `[blocking]` が1件以上ある場合だけです。`[non-blocking]` だけの場合は `STATUS: PASS` とし、レポートの「Non-blocking findings」節に列挙します。これらは差し戻し回数に数えず、オーケストレーターも差し戻しません。最終報告とPR本文の「未対応の指摘」に、件数と内容を載せます。
   - オーケストレーターは、レビュワーが付けた `[blocking]` を自分で `[non-blocking]` に変更したり、免除したりしません。分類に疑義がある場合は、レビュワーに再分類の根拠を求めます。上限に達した場合は、従来どおりBlockedとして人間に報告します。
3. **合否判定プロトコルと監査ログ（Attempt退避）**:
   - 各ステップのレビュワーおよびQAは、常に最新の判定を `review-step<N>.md`（または `qa-report-step5.md`）に出力します。
   - ファイルの先頭行には `STATUS: PASS`、`STATUS: FAIL`、または人間の判断待ちの場合に限り `STATUS: BLOCKED` を明記し、指摘事項や判定理由を箇条書きで具体的に記述します。
   - **リトライ履歴の退避**: 差し戻しが発生して再レビュー/再テストを行う際、前回のレポートは `review-step<N>-attempt<M>.md`（QAの場合は `qa-report-step5-attempt<M>.md`）として退避・保存し、常にイテレーションの差分履歴を追跡可能にします。
   - オーケストレーターは該当ファイルの先頭ステータスを読み取り、次ステップへの進行または差し戻しを機械的に判定します。
4. **機密情報とソースデータの保護**:
   - 取得前に、ソースデータをローカル保存できるか確認します。認証情報、アクセストークン、個人情報、機密性の高い本文は、タスクに必要な最小範囲だけ扱います。
   - 機密性の高い生データは `sources/` に保存しません。保存が必要な場合は、機密情報を除去またはマスキングした最小限の抜粋を保存します。
   - 保存したソースは `.git/info/exclude` に登録し、コミット前に `git status` とステージ済みファイルを確認します。除外設定だけを安全性の根拠にしません。
   - PRやコミット対象の文書に、非公開ソースの本文、個人情報、認証情報を転載しません。必要な根拠は、公開可能な要約と取得日時、参照先で示します。
   - `task-background.md` から非公開のローカルファイルをリンクする場合は、リンク先がPR上で閲覧できないことを明記し、レビューに必要な根拠を公開可能な要約として記載します。
   - 機密情報が混入した可能性を排除できない場合は、ステージング・コミット・pushを保留し、人間に報告します。
5. **Herdrペイン・リソース管理とエージェント起動コマンド**:
   - タスク開始時に専用タブを1つ作成します。
   - ステップごとに必要なペインを分割（`herdr pane split`）して該当エージェントを起動（`herdr agent start`）します。
   - **エージェント起動オプションと初期化手順**:
     - **Codex (`codex`)**:
       - 自動承認で自律実行させるため、起動時に必ず `--approve-for-me` オプションを付与します。
       - 起動コマンド例:
         ```bash
         herdr agent start <agent-name> --kind codex --pane <pane-id> -- --approve-for-me
         ```
     - **Antigravity CLI (`agy`)**:
       - `agy --sandbox --mode=auto` は環境によって機能しない場合があるため、`--sandbox` で起動後に Herdr で `shift+tab` を2回送信して `auto` モードに切り替えます（現行バージョンでは2回送信で auto モードになります）。
       - 起動およびモード切替コマンド例:
         ```bash
         # 1. sandbox モードで起動
         herdr agent start <agent-name> --kind agy --pane <pane-id> -- --sandbox

         # 2. 起動後、shift+tab を2回送信して auto モードへ変更
         herdr agent send-keys <agent-name> shift+tab
         herdr agent send-keys <agent-name> shift+tab
         ```
     - **Claude Code (`claude`)**:
       - 意図せず `accept edits on` などのモードで起動するのを防ぎ、完全自律実行させるため、起動時に必ず `--permission-mode auto` を指定して auto モードで起動します。
       - 起動コマンド例:
         ```bash
         herdr agent start <agent-name> --kind claude --pane <pane-id> -- --permission-mode auto
         ```
   - **待機ルール（トークン節約）**: ペインの出力を繰り返し読んで完了を確認しません。確認のたびに、オーケストレーターの文脈全体が再読込されるためです。
     - 作業やレビューの依頼は `herdr agent prompt <agent-name> "<ファイルを読んで従う旨の指示>" --wait --timeout <ms>` で送り、`idle` / `done` / `blocked` になるまで1回で待ちます。長い作業では `--timeout` を長めに指定します。
     - `timeout` になった場合は、`herdr agent get <agent-name>` で状態を1回確認し、`working` なら `herdr agent wait <agent-name>` で再度待ちます。`blocked` の場合だけ `herdr agent read` で内容を確認します。
     - 結果は、完了後に成果物ファイル（`review-step<N>.md` の先頭行など）を1回だけ読みます。待機中に `sleep` と `pane read` を繰り返しません。
     - 複数のペインで並行して作業できる場合は、それぞれに依頼を送ってからまとめて待ちます。
   - ステップ完了（PASS）時に該当ステップのペインをクローズし、メモリ・トークン消費とコンテキスト肥大化を防止します（成果物はファイル経由で引き継がれます）。
6. **Gitブランチ運用**:
   - タスク開始時に専用のフィーチャーブランチ（`feature/<task-name>`）を自動作成します。
   - Step 5の全検証完了後、機密情報とユーザーの既存変更を除く成果物（ドキュメント群、実装コード、テストコード、QAレポート、レビューログ）をコミットし、リモートへプッシュしてDraft PRを作成します。

## 各ステップの詳細手順と合格基準

### Step 1: Collect (情報収集)
- **入力**: スキル引数に示された自然言語による情報ソース（GitHub, Notion, Slack, Google Drive, カレントディレクトリ内のメモファイル等）。
- **外部アクセス前提とエラー時対応**:
  - 指定ソースごとに「必須」または「任意」を記録します。任意ソースにアクセスできない場合は、未取得として記録して続行します。必須ソースにアクセスできず、他の情報から安全に代替できない場合は、Step 1を保留して人間に報告します。
- **作業者 (Claude Code - `--permission-mode auto` 指定)**:
  1. 指定された各ソースからタスクに関連する情報を取得します。
  2. 保存が許可されている場合に限り、レビューに必要な最小限のデータを `sources/` に保存します。機密性の高い生データは保存せず、必要な抜粋は機密情報を除去またはマスキングします。
  3. `task-background.md` に背景情報をまとめ、どの情報をどのソースから取得したかを **IEEE Reference Style** で明記します。非公開のローカルファイルを参照する場合はPR上で閲覧できない旨を記載し、公開可能な根拠の要約も添えます。
- **レビュワー (Antigravity CLI - `agy --sandbox` 起動後に `shift+tab` × 2 で auto 化)**:
  - `task-background.md` のIEEE引用と、参照可能な元ソースまたは `sources/` 内の保存可能なデータを突合します。保存されていないソースはアクセス可能な範囲で確認します。
  - 元ソースとの矛盾や、ソースが存在しないハルシネーションがないかを精査します。
  - `review-step1.md` に `STATUS: PASS` または `STATUS: FAIL` と検証結果を出力します。ハルシネーションや矛盾が見つかった場合は作業者に差し戻します。

### Step 2: Analyze (要件定義)
- **入力**: `task-background.md`
- **作業者 (Antigravity CLI - `agy --sandbox` 起動後に `shift+tab` × 2 で auto 化)**:
  1. 高度なNLP能力を活かして `task-background.md` を要求仕様にまとめ、`PRD.md` を作成します。
  2. 機能要件および測定可能な非機能要件（性能・セキュリティ・可用性等）を半形式手法的に **Given... When... Then...** 形式で網羅的にリスト化します。
  3. 「前提条件・制約・スコープ外」セクションを独立して明記します。
  4. 背景情報に矛盾があった場合、最も合理的に整合すると思われる形に統合し、「矛盾点」「統合結果」「判断根拠」を記録する専用セクションを設けます。
  5. 根本的に相反するビジネス要求がありAIの推論のみで解決できない場合は、「要人間判断（Pending Human Decision）」として明記し、無理な仮定を置かないようにします。
- **レビュワー (Codex - `--approve-for-me` 付与)**:
  - Codexの論理的厳密性を活かし、`task-background.md` と `PRD.md` 間の抜け漏れ・齟齬を精査します。
  - Given-When-Thenの境界条件や前提の漏れを検証します。
  - **矛盾解決の合否基準**: レビュワー自身の主観的好みで合否を判定するのではなく、「矛盾点・統合結果・判断根拠が論理的に筋が通っているか」を判定基準とします。論理的破綻がある場合は `STATUS: FAIL`、論理的に整合していれば `STATUS: PASS` とします。解決不能な重大事項が「要人間判断」として提起されている場合、Codexは `STATUS: BLOCKED` と理由をレビューに記録します。`BLOCKED` はPASS/FAILとは別の状態とし、該当要件に依存する作業を保留します。独立した作業は続行できます。

### Step 3: Define (テスト仕様策定)
- **入力**: `PRD.md`
- **テスト分類の明確な境界基準**:
  - **1. 決定論的自動テスト (最優先)** ➔ `automated-tests.md`:
    - コードスクリプトとして完全に決定論的・再現可能に記述できるもの。ユニットテスト、結合テスト、および **Playwright / Cypress などのスクリプト化可能なブラウザE2Eテスト** はすべてここに含まれます。
  - **2. エージェント操作による確率論的テスト** ➔ `agentic-tests.md`:
    - 固定スクリプト化が難しく、LLMやビジョンモデルが画面の文脈・レイアウト・自然言語応答を解釈しながら試行錯誤・探索的に操作・視覚検証する必要があるもの（非構造的UIの探索、デザイン崩れ・レイアウト崩れの視覚確認、LLM出力の文脈判定など）。
  - **3. 人間による手動確認 (最終手段)** ➔ `manual-tests.md`:
    - 人間による実機確認、決済連携、外部組織との協調、法的・運用的な目視確認など。
- **作業者 (Claude Code - `--permission-mode auto` 指定)**:
  - PRDの全要件（Given-When-Then）を上記優先度（1 > 2 > 3）で分類し、テスト仕様書（ID, 対応PRD要件ID, 入力, 期待値, 実行手順/コマンド案）を策定します。
- **レビュワー (Codex - `--approve-for-me` 付与)**:
  - PRDの全要件がいずれかのテストでカバーされているか（網羅性）を確認します。
  - 自動テスト（スクリプト化）可能なものがエージェントテストや手動テストに割り振られていないか（優先度ルールの厳守）を精査します。
  - 記載の手順で客観的にテスト可能かを検証し、`review-step3.md` を作成します。

### Step 4: Architect (システム詳細設計)
- **入力**: `PRD.md`, `automated-tests.md`, `agentic-tests.md`, `manual-tests.md`
- **作業者 (Claude Code - `--permission-mode auto` 指定)**:
  1. 既存コードベースのアーキテクチャ・命名規則・ディレクトリ構造を探索した上で、要件およびテスト仕様を満たす詳細設計を `system-design.md` にまとめます（アーキテクチャ図、データモデル/スキーマ、API/インターフェース設計、コンポーネント構成）。
  2. **ISO/IEC 25010 の8品質特性対応表** を設け、変更に関係する特性への設計上の対策を記載します。関係しない特性は「該当なし(N/A)」と根拠を簡潔に記載します。小規模な変更では表を簡略化できますが、セキュリティや信頼性など影響が見込まれる項目は評価を省略しません。
     - 機能適合性 (Functional Suitability)
     - 性能効率性 (Performance Efficiency)
     - 互換性 (Compatibility)
     - 使用性 (Usability)
     - 信頼性 (Reliability)
     - セキュリティ (Security)
     - 保守性 (Maintainability)
     - 移植性 (Portability)
- **レビュワー (Codex - `--approve-for-me` 付与)**:
  - 設計が必要十分であり、PRDおよび各テスト仕様を漏れなくカバーしているかを確認します。
  - 過剰設計（YAGNI違反）や設計不足、既存コード規約との著しい不整合がないかを精査します。
  - 8つの品質特性観点で設計上のリスクや抜け漏れ、未考慮事項がないかを厳格に精査し、`review-step4.md` を作成します。

### Step 5: Implement (実装・QA・最終監査)
- **入力**: `system-design.md`, `automated-tests.md`, `agentic-tests.md`, `manual-tests.md`
- **作業者 (Claude Code - `--permission-mode auto` 指定)**:
  - 設計および自動テスト仕様に基づき、プロダクションコードおよび自動テストコード（ユニット/結合/E2Eスクリプト）を実装します。
- **QA (Antigravity CLI - `agy --sandbox` 起動後に `shift+tab` × 2 で auto 化) — テスト環境ライフサイクル管理**:
  1. **サーバー起動とヘルスチェック**: WebアプリやAPIのテストが必要な場合、QAエージェント自身がバックグラウンドプロセスでローカル開発サーバー（例: `npm run dev`）を立ち上げ、疎通確認（HTTP 200等のヘルスチェック）を確認します。
  2. **テスト実行**:
     - `automated-tests.md` に基づく自動テストコマンドを実行し、エビデンス（実行ログ、終了コード）を取得します。
     - `agentic-tests.md` に基づく操作手順を実走します（特にGoogle Chromeや `terminal-browser` を用いた自律的UI/視覚シナリオ操作を行い、ログやキャプチャを取得）。
  3. **サーバー停止**: テスト実走完了後、起動したローカルサーバープロセスを確実にクリーンアップ・停止します。
  4. **レポート出力**: テスト結果を `qa-report-step5.md` にまとめます。未達テストがある場合は `STATUS: FAIL` として作業者に差し戻します。全テストが成功した場合は `STATUS: PASS` とします。手動確認が残る場合は、未実施項目と実施主体を明記します。結果を信頼できる形で取得できない場合はPASSにせず、理由を記録して納品を保留します。
- **レビュワー (Codex - `--approve-for-me` 付与)**:
  - QAがすべてPASSした後、`qa-report-step5.md` のエビデンスの妥当性（テストの形骸化、モックによる偽陽性、アサーションの抜けがないか）を厳格に監査します。
  - 実装コードの差分（`git diff`）を精査し、設計との適合性、コード品質、セキュリティ面をレビューし `review-step5.md` を作成します。
  - **差し戻しルール**: レビューでFAILとなった場合、作業者に修正させ、**修正後は必ず再度QA（Antigravity CLI）によるテスト実走を通してエビデンスを更新してから再レビュー**を行います。

## 完了・納品処理 (Draft PR作成)

Step 5のレビューが `STATUS: PASS` に達したら、オーケストレーターは以下の納品処理を実行します:

1. `sources/` が `.git/info/exclude` によってGit管理から除外されていることを再確認します。
2. コミット前に変更ファイルとステージ済みファイルを確認し、依頼された変更、生成した成果物、レビュー・QAレポートだけを含めます。ユーザーの既存変更、`sources/`、秘密情報を含むファイルがあればコミットを保留します。
3. 適用するステップがすべてPASSし、保留中の重大判断がなく、コミット対象に機密情報が含まれないことを確認してから、成果物をステージングしてコミットします。
4. リモートブランチへプッシュ: `git push -u origin feature/<task-name>`
5. GitHub CLI (`gh`) を使用して **Draft PR** を作成します:
   ```bash
   gh pr create --draft --title "feat: <task-title>" --body-file - << 'EOF'
   ## Summary
   <!-- task-background.md からの背景要約 -->

   ## Requirements & Design
   - PRD: [PRD.md](./PRD.md)
   - System Design: [system-design.md](./system-design.md)
   - Test Specs: [automated-tests.md](./automated-tests.md) / [agentic-tests.md](./agentic-tests.md)

   ## QA & Test Evidence
   - Automated & Agentic Tests: **STATUS: PASS**
   - 詳細エビデンス: [qa-report-step5.md](./qa-report-step5.md) 参照
   - 最終コード監査: [review-step5.md](./review-step5.md) (Codex Review: PASS)

   ## Open Non-blocking Findings
   <!-- レビュー・QAの [non-blocking] 指摘の件数と内容。なければ「なし」 -->

   ## Manual Verification Checklist (Human QA)
   以下はマージ前または本番リリース前に人間が手動で確認すべき項目です（manual-tests.md より抽出）:
   - [ ] <手動確認項目1>
   - [ ] <手動確認項目2>
   EOF
   ```
   軽量版では、`Requirements & Design` の PRD / System Design / Test Specs の行を、`plan.md` へのリンク1行に置き換えます。
6. ユーザーに完了報告とPRのURLを提示して終了します。
